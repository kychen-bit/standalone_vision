# 环境光鲁棒色块识别

规则取消了向下补光后，同一块物料会在不同场馆、不同时间段被不同的环境光照到。
固定 HSV 阈值只对"调参那一刻的光"成立，这是当前
`config/jetson.json` 里颜色参数仍标着 `TEMPORARY SCREEN TEST` 的原因。

本文说明现在的做法、怎么用、以及什么情况下才需要考虑训练模型。

## 1. 结论：先做颜色恒常性，不要先上 YOLO

| 方案 | 成本 | 解决的问题 |
|---|---|---|
| 逐帧白场归一化 + 色块级最近邻分类（本方案） | 无标注、无训练，约 3 ms/帧 | 色温、亮度、阴影渐变导致 HSV 漂移；蓝/浅蓝、黑/阴影重叠误判 |
| YOLO / 分割模型 | 标注数据、训练、TensorRT 部署 | "在哪、是什么形状"；对**色偏本身没有免疫力**，仍要靠颜色恒常性做预处理 |

比赛里颜色是低维问题（6 个色号、已知几何形状），而决赛若出现组合体、遮挡、
杂乱背景，检测能力才真正变重要。所以顺序是：先把颜色做稳，再考虑小模型。

## 2. 现在的识别链路

```text
原始帧
  → 白场归一化（每帧估计光源色温与亮度，重新曝光）
  → HSV inRange 得到各色掩码
  → 轮廓 / 凸包 / 面积 / 边界过滤（与原来一致）
  → 按"整块物料的均值颜色"在每个色号上算距离分
  → 一轮三件用互异指派（3! 全排列取总分最大）定色
  → 多帧投票确认
```

### 2.1 白场归一化（`jetson_recognition/illumination.py`）

场地本身就是标定板：工作面是亚光白色，转盘周围一定看得到一块已知的中性面。
每帧从这个中性面估计光源：

- 取降采样子图，用 `S ≤ 阈值` 找中性（灰白）像素，取其 `V` 作为亮度；
- 各通道分别取 88 分位作为白场电平 → 得到光源的三通道比例；
- 增益 = `canonical_level / 白场电平`，用一张 256 项 LUT 把整帧重新曝光，
  使白场永远落回 `canonical_level`（默认 235）。

这样 HSV 里的 `V` 就变成"反射率"而不是"环境亮度"，色温带来的偏色也被除掉，
一组阈值可以覆盖偏暗、偏暖、偏冷的场馆。

保护机制：

| 情况 | 行为 |
|---|---|
| 找不到中性面（画面里没有白场） | 不处理，原帧直通，`reason=NO_NEUTRAL_REFERENCE` |
| 白场被削顶（`value ≥ 250` 的占比过高） | 不处理，`reason=WHITE_FIELD_CLIPPED`（削顶后无法恢复，只能降曝光） |
| 相邻帧白场突变（手臂伸进画面） | 不跟随，按 `hold_smoothing` 慢速漂移，`reason=HELD_ABRUPT_CHANGE` |
| 增益接近 1（`|gain-1| ≤ gain_epsilon`） | 跳过整帧 LUT，几乎零开销 |

诊断字段在 `detector.last_illumination`：`white_ref_bgr`、`gain`、`reliable`、
`reason`、`overexposed_ratio`、`reference_mode`（STRICT/RELAXED）。

### 2.2 色块级分类（`color_detection.label_classifier`）

`hsv_ranges` 同时充当"原型"：颜色样本先看是否落在某个色号区间内，再按
`hue/saturation/value` 三个方向的加权距离选最近的色号。距离里带一个很小的
"靠近区间中心"项，用来拆开区间重叠的情况（绿与浅蓝在色相上重叠、黑与浅蓝在
亮度上重叠）。**不需要人工标注**，调参位置仍然是那 6 组 `hsv_ranges`。

### 2.3 一轮批次与互异指派（`jetson_recognition/color_batch.py`）

一轮转盘上就是这一轮的三种颜色，所以问题不是"这块是不是我要的颜色"，而是
"这三块分别是什么颜色"。因此：

- `detector.detect_materials(frame, scene, [轮次颜色])` 返回**每一块物料**的中心、
  色号、置信度，以及它对 6 个色号的距离分；
- `assign_distinct()` 在"三块 ↔ 三色"的所有排列里取总分最大的那个，天然不允许
  两块物料被判成同一个色号；
- `assignment_margin()` 给出最优与次优的差距，差距太小说明这一帧不能信。

`detect_color()`（正式 `coordinator` 用的单色路径）行为不变，只是输入帧换成
归一化之后的帧，所以整机链路也同时受益。

## 3. 怎么用

### 3.1 现场测试（推荐入口）

```bash
sudo systemctl stop standalone-vision.service      # 相机独占
python3 tools/test_turntable_color_live.py \
  --task-code 156+123+516+231 --batch 1 --target 1
```

窗口里画的是**归一化之后的画面**（探测器真正看到的东西），底部显示
`LIGHT <reason> ref=[...] gain=[...]`，鼠标探针也读这个画面，所以读数与阈值一致。

JSON 里每帧会输出：

```text
round_batch        本轮判定的三个色号
batch_agreement    最近 N 帧的一致率
batch_stable       连续 N 帧完全一致
materials[]        每块的 blob_id/assigned/center_px/confidence/distance/margin/area
assignment_gap     最优指派与次优指派的差距
illumination       白场诊断
```

A/B 对照：

```bash
--no-illumination   # 关掉白场归一化，回到"原始 HSV"行为
--no-batch          # 回到逐色号独立掩码（旧的 detect_colors 路径）
```

换光照重测：把灯换成暖色/冷色、遮挡部分环境光、把物料放到阴影里，观察
`round_batch` 是否稳定、`materials[].distance` 是否变大。

### 3.2 颜色阈值要不要重调

归一化后白场固定在 235，`V` 的含义变了（≈白场比例），所以：

- 如果原来调参时光照下白场就在 235 附近，阈值基本可以直接用；
- 否则用 `live --show-hsv` 或上面的工具按新读数微调一次 `v_min`；
- 因为有了色块级分类，`hsv_ranges` 只需要保证"物料的主要像素落在自己的区间里"，
  不必再为了排出别的颜色把区间卡得很窄。**建议把各色的 `v_min` 适当放宽**
  （例如原来的 160 改成 120），让掩码更容易连成整块，颜色由距离分决定。

单色查看：

```bash
python3 -m jetson_recognition.run live \
  --mode COLOR --scene TURNTABLE --target red --show-hsv --show-mask
```

### 3.3 已知限制

- **白场被削顶**：`overexposed_ratio` 高或 `reason=WHITE_FIELD_CLIPPED` 时，
  归一化会自动关闭。这时应降低 `exposure_time_absolute`，让白场落在 200～240，
  而不是指望算法恢复。
- **全场都是物料**：画面里看不到白场时归一化直通，退化为原行为。
  转盘场景的自然背景足够，粗加工/暂存区的 `object_roi` 也包含地面。
- **黑色与阴影**：阴影在数值上与黑色物料接近；目前靠凸包/圆度/长宽比等形状
  约束区分（与改动前一致）。若现场阴影严重，优先调整机位与补光角度。
- 只做了整帧（低频）归一化，不纠正强局部阴影。局部阴影退化为"亮度下降"，
  由 `v_min` 的余量吸收。

## 4. 有无补光的开关

顶层 `lighting.fill_light` 是总开关：

| 取值 | 含义 | 行为 |
|---|---|---|
| `true` | 有向下补光，光照稳定 | 关闭逐帧白场归一化，直接用锁定的相机参数和现场标定的 HSV 阈值（即改动前的行为） |
| `false` | 无补光（本届规则，默认） | 启用白场归一化 + 一轮批次互异指派判色 |

临时切换（不改 JSON）：

```bash
python3 tools/test_turntable_color_live.py --task-code 234+123+432+231 --batch 1 --target 3 --fill-light
python3 tools/test_turntable_color_live.py --round-colors 2 3 4 --target 3 --no-fill-light
```

启动时会打印一行 `LIGHTING_MODE`，带 `fill_light`、`illumination_enabled` 和已配置的标定点，
先看这行再开始调参。`color_detection.illumination.enabled` 仍然有效，
但 `fill_light: true` 会无条件把它关掉。

两种模式的 `v_min` 含义不同（补光模式是原始亮度，无补光模式是相对白场的比例），
所以要**各自调一次**，不要指望一套阈值通吃两种模式。

### 4.1 两套参数分开存：`config/color_profiles.json`

`config/jetson.json` 里的 `colors.*` 保持**有补光时标定的那一套**（那是你之前对着
补光调出来的）；无补光的差异只写在 `config/color_profiles.json`，启动时按开关自动
深合并上去：

```jsonc
{
  "fill": {},                     // 有补光：留空 = 用 jetson.json 的原值
  "ambient": {                    // 无补光：只写要覆盖的键
    "colors": { "2": { "prototype_hsv": [28.4, 96.2, 128.7] } },
    "color_detection": { "geometry": { "min_mass_ratio": 0.30 } }
  }
}
```

* `lighting.fill_light = true` → 用 jetson.json 的值，`ambient` 节完全不生效。
* `lighting.fill_light = false` → 把 `ambient` 节深合并覆盖 `colors` / `color_detection`，
  **只写了的键才会被覆盖**，其它键保留 jetson.json 的值。
* 启动会打印 `COLOR_PROFILE`，能看到当前用的是哪一节、覆盖了哪几个色号。
* 在实时工具里按 `w` 保存原型时：无补光模式写进 `color_profiles.json` 的 `ambient` 节，
  有补光模式写回 `jetson.json`。所以以后再也不会用无补光的采样值
  覆盖掉你有补光时的那套标定（每次写盘前都有 `.bak` 备份）。
* 想手改某个色号的 V 下限，只补那一段就行；注意 `hsv_ranges` 是列表，写了就是整段替换。
  更推荐的做法是**不要改区间**，直接在实时工具里指物料按 `1`~`6` 采原型。

### 4.2 黑色必须是【暗 + 低彩度】（2026-09-18 实测修正）

黑色以前的门限是 `v_max: 80, s_max: 255`，**没有任何彩度限制**：任何 `V ≤ 80` 的像素都算黑。
真实场景里机械臂末端挡住补光、物料落进阴影时，物料的 **V 掉到 80 以下但 S 仍然是 255**
（S 在光照纯缩放下不变），于是"红色、浅蓝全被识别成黑色"。同一帧 A/B 实测：

```text
改前（s_max=255）：黑掩码 150 819 px，最大块 128 084 px，中位 H=0 S=255 V=18  ← 那是阴影里的红料
改后（s_max= 90）：黑掩码  27 601 px，最大块  11 684 px，中位 H=0 S=  0 V= 0  ← 这才是真黑（边角纯黑区）
```

结论：`s_max` 是分开"黑料"与"阴影里的彩料"的关键，`v_max` 只负责"暗"。
若真黑料在暗光下 S 超过 90，把 `s_max` 提到 110~130，**不要**放回 255。

### 4.3 v_min 不要降到噪声地板以下

`v_min` 看着像"阴影容差"，但把红料的 `v_min` 从 140 降到 55 之后，同一帧实测
红掩码从 10.2 万 px 涨到 **28.7 万 px**（最大外轮廓包面积 41 万 px，中位 S=204 V=118）——
那些是归一化把暗帧放大 2~3 倍后的**彩色噪声**，不是物料。所以：

* `v_min` 取"标称亮度的一半左右"，并且明显高于噪声地板（现在 80 / 85 / 85 / 80 / 70）。
* 真阴影里的物料掉到噪声地板以下时，降 `v_min` 救不回来 —— 那是曝光/补光问题。
  低于地板时宁可"认不出来"（`TARGET_LOST`），也不要猜成错的颜色：
  错颜色会毒化整轮的互异指派。

### 4.4 白场是归一化的前提：`NO_NEUTRAL_REFERENCE`

暖光下"整个桌面"都满足红色阈值（实测暗暖帧里 21 万 px 是 `H≈6 S≈154 V≈88`）。
能把它们压回去的只有白场归一化，而它需要画面里**真的有一块白场**。
实测 `neutral_ratio`：健康场景 0.06~0.27，病态帧 0.023（几乎没有白场）。
`min_neutral_ratio` 已从 0.02 提到 **0.05**：白场不足时归一化直接**拒绝执行**，
并在诊断里给出 `reason=NO_NEUTRAL_REFERENCE`，宁可让阈值作用在原图上，也不拿
一个坏的白场估计去放大噪声。所以：

```text
看到 reason=NO_NEUTRAL_REFERENCE  → 画面里放一块白（白纸/白环），或把 ROI 对准白环
看到 exposure_hint=RAISE_EXPOSURE → 先抬曝光/gain，再谈颜色
看到 clipped_ratio 高             → 降曝光（补光灯太亮时用 --camera-profile fill_light_locked）
```

实时工具的状态行现在会打印 `LIGHT <reason> ref=... gain=... n=<neutral_ratio> <hint>`，
`n` 就是这个可信度。

## 5. 曝光：先看 gain，再怀疑算法

白场归一化只能修正光源色温和**小幅**亮度差。一帧本身就欠曝的图，归一化是在放大噪声，
这才是掩码碎成斑点、颜色跳变的常见原因。诊断里的 `gain` 与 `exposure_hint` 就是干这个的：

| `exposure_hint` | 含义 | 动作 |
|---|---|---|
| `RAISE_EXPOSURE` | 需要的增益 > `exposure_gain_max`（或已顶到 `max_gain`） | 加大 `exposure_time_absolute` / 补光，直到 gain 回到 0.9~1.3 |
| `OK` | 增益在 0.9~1.6 之间 | 正常 |
| `LOWER_EXPOSURE` | 画面明显偏亮 | 减小曝光，否则高光会被削顶 |
| `WHITE_FIELD_CLIPPED` | 白场被削顶（`clipped_ratio` 过高） | 减曝光；削顶的信息无法恢复 |

本机实测（工作台偏暗时的真实读数，仅用于演示趋势）：

```text
exposure= 50  white_ref=[66, 77, 125]   gain=[3.58, 3.04, 1.88]  hint=RAISE_EXPOSURE
exposure=120  white_ref=[83, 103, 150]  gain=[2.82, 2.28, 1.57]  hint=RAISE_EXPOSURE
exposure=200  white_ref=[138, 145, 195] gain=[1.71, 1.62, 1.20]  hint=OK
exposure=400  white_ref=[195, 201, 255] gain=[1.21, 1.17, 0.92]  hint=OK（约 10% 过曝）
```

结论：先把 `exposure_hint` 调到 `OK`，再动颜色阈值。

### 5.1 曝光的物理上限不是 10000，而是 1/fps

本机（DECXIN UVC）实测控制范围：

| 控制 | 范围 | 单位 | 备注 |
|---|---|---|---|
| `exposure_time_absolute` | 1 ~ 10000 | **100 µs** | 即 0.1 ms ~ 1 s；必须 `auto_exposure=1`（Manual）才生效 |
| `gain` | 0 ~ 255 | - | 先动曝光再动 gain，gain 是纯放大，噪声同步放大 |
| `focus_absolute` | 0 ~ 1023 | - | 手动对焦，无自动对焦档；换机位高度必须重对 |
| `white_balance_temperature` | 2800 ~ 6500 | K | 锁定，别让 AWB 乱跳 |
| `zoom_absolute` | 0 ~ 60 | - | 只能变窄，且流没建立时写不进去 |

**关键约束**：一帧只有 1/fps 秒，传感器不可能积分更久。超过帧时长的曝光值，
驱动虽然会写进去，但图像不再变亮、帧率开始抖：

| 采集档位 | 一帧时长 | 可用曝光上限 |
|---|---|---|
| `default` 1280x720@60 | 16.7 ms | ≈ 166 |
| `dim_30fps` 1280x720@30 | 33.3 ms | ≈ 333 |

2026-09-18 实测（50 Hz 室内灯、默认档位、gain=0）：

```text
expo=100 (10 ms)  ref=none         hint=UNKNOWN  p99V=43~89    ← 白场都找不到，这就是晚上不 OK 的原因
expo=150 (15 ms)  ref=none         hint=UNKNOWN  p99V=66
expo=200 (20 ms)  ref=[134,154,214] hint=OK      p99V=200
expo=266 (26 ms)  ref=[129,151,208] hint=OK      p99V=199
expo=333 (33 ms)  ref=[92,119,176]  hint=RAISE_EXPOSURE p99V=174  ← 超了 60fps 的帧时长，反而更暗
```

gain 扫描（曝光固定 200，同样照明）：

```text
gain= 2  ref=[132,154,211] 归一化增益=1.47  hint=OK  p999V=217  ← 保守
gain=12  ref=[141,161,220] 归一化增益=1.40  hint=OK  p999V=247  ← 实测最优点，不削顶
gain=16  ref=[145,165,226] 归一化增益=1.36  hint=OK  p999V=255  ← 蓝通道开始削顶
```

所以暗环境按顺序做：

1. 先按一次诊断看 `exposure_hint`，欠曝就加曝光。
2. 需要 >166 的曝光（很暗的场地）就把采集档换到 `dim_30fps` 再上曝光，
   **不要**在 60fps 档位上把曝光硬拉到 300+。
3. 曝光够不着时再加 `gain`，每一步用 `p999V` 检查有没有削顶：**任何一个通道到 255，
   颜色就不可信了**（蓝通道削顶会让"浅蓝"和"白场"分不开）。
4. 削顶优先减 gain，再减曝光。

已按上面的实测值存好一个档位，直接切换即可：

```bash
python3 tools/test_turntable_color_live.py --camera-profile dim_room_locked ...   # 曝光200 / gain12
python3 tools/test_turntable_color_live.py --camera-profile dim_room_locked --capture-profile dim_30fps ...
```

### 5.2 换机位高度要重做的事

高度一变，**面积**和**对焦**变，颜色本身没变：

| 变了什么 | 要重做什么 | 不要做什么 |
|---|---|---|
| 相机高度 / 工作距离 | 重对焦（`focus_absolute`，750 是旧高度调的）；用工具 `d` 键看 `recommended_area` 重定 `min_area` | 不要重标 HSV；不要拿 `max_area` 卡紧（曾按高机位写 60000，降高度后红料直接被拒） |
| 环境光强弱 | 调曝光/gain 让 `exposure_hint=OK`、`neutral_ratio` 稳定 | 不要重标 HSV：白场归一化已经把亮度变化归一化了 |
| 光照**色温**变了 | 也先靠归一化；若 `wb_gain` 稳定偏大，再动 `white_balance_temperature` | 不要让 AWB 开着 |
| 换了镜头/视场档（`wide_4_3`） | 重画 ROI、重采圆环数字模板、重定面积门限 | 不要沿用旧 ROI |

"颜色不准"要分清是哪一种：打开 `d` 诊断看每个色号的 `core_hsv` 是否落在该色号的
`hsv_ranges` 里。落进去了说明标定没问题，是**阈值之外**的，就该查曝光/形状过滤；
完全没落进去才需要改那个色号的范围——而且只需要动那一个色号。

## 6. 形状过滤（按物料几何建模）

先看物料长什么样：赛题图 5 的初赛物料是**圆台**——顶部 φ30 面（高 8 直边）、中间锥面
φ30→φ50（高 60）、底部 φ50 直边 8。相机从上往下看，得到的是：

```text
    俯视 = 两个同心圆
    ┌───────────────┐
    │   φ30 顶面     │  ← 正对相机，颜色最准（占面积 36%）
    │  (填充圆盘)    │
    │ ┌───────────┐ │
    │ │  φ50 底面  │ │  ← 中间的锥面在斜面上，受光不一样，
    │ └───────────┘ │     常常落在**另一个色号**的区间里 → 表现为一个"环"
    └───────────────┘
```

这个几何决定了干扰的形状：**真物料是"填充圆"，干扰往往是"环"或"碎片"**。
`color_detection.geometry` 里真正管用的门限（实测数据）：

| 参数 | 含义 | 实测参考 | 默认 |
|---|---|---|---|
| `min_mass_ratio` | 凸包内**真实掩码像素**占比 | 实心 1.00；圆+反光缺口 0.80；不规则六边形 0.83；交叉标记 0.25；空心环 0.25；锥面环 0.64 | **0.35** |
| `max_hole_ratio` | **最大内洞面积 / 轮廓面积** | 实心/缺口/碎裂全都 0.00；空心环 0.77；φ30-φ50 锥面环 0.36 | **0.30** |
| `min_aspect_ratio` / `max_aspect_ratio` | 外接矩形长宽比 | 细长条被卡住 | 0.65 / 1.55 |
| `min_area` / `max_area` | 凸包面积上下限 | **场景里默认 700/500000 太松**，见下 | 按实测 |
| `min_contour_circularity` | 轮廓自身圆度 | 反光缺口 0.41 反而比撕裂阴影 0.70 更低 → **分不开，默认关闭** | 0.0 |
| `black_min_circularity` | 黑色的圆度 | 区分阴影与黑色物料 | 0.7 |

两个必须知道的点：

1. **凸包圆度/凸包四边形度都没用**：`circularity` 与 `solidity` 都是算在凸包上的，
   任何凸的东西都接近 1，等于没滤——这也是以前"形状过滤不起作用"的原因。
   真正起作用的是 `mass_ratio`（真实像素占比）与 `hole_ratio`（有没有内洞）。
2. **锥面环会被自动认领**：`_materials_in_roi` 里有一条规则——若某个色块的内洞
   正好套着另一个色块的中心（且内块面积 ≥ 洞面积的 25%），就判定这个环是内块的锥面，
   不当作独立物料上报（工具 JSON 里的 `rings_explained` 会记录）。

### 6.1 用一秒诊断代替猜

在实时工具窗口里按 `d`（或加 `--dump-every 30`）会打印一份完整体检，
并在 `logs/diag_*.png` 存下当前帧和六色掩码拼图：

```json
{"state":"DIAGNOSE",
 "illumination":{...gain/exposure_hint/reliable...},
 "colors":{"1":{"mask_px":13673,"mask_hsv_median":[0,0,200]},
           "2":{"mask_px":13673,...},
           "3":{"mask_px":0,...}},          // ← 掩码为 0 就是"根本没圈到像素"
 "materials":[{...core_hsv、distance、mass_ratio、hole_ratio、equivalent_diameter...}],
 "filter_stats":{...每个色号被哪一种门限拒了多少个...},
 "recommended_area":{"min_area":13256,"max_area":94687}}
```

看三件事就能定位问题：

| 现象 | 结论 | 动作 |
|---|---|---|
| 某色号 `mask_px` = 0，但物料就在画面里 | 阈值把物料像素排除了 | 看 `mask_hsv_median` 与 `colors.<id>.hsv_ranges` 的差距：只放宽对应的 `v_min`/`s_min`，或按该色采原型 |
| `mask_px` 很大但 `materials` 为空 | 形状/面积门限拒了 | 看 `filter_stats` 里哪一项在涨：`mass_rejected` → 碎片；`hole_rejected` → 环；`area_rejected` → 面积 |
| `materials` 里 `distance` 很大 | 判色原型不匹配 | 鼠标指物料按对应色号采原型（第 7 节） |

**面积门限一定要按自己机位设**：把上面 `recommended_area` 的两个数（= 实测最大物料面积的
0.35~2.5 倍）写进 `scenes.TURNTABLE.min_area/max_area`。现在场景里是 700/500000，
相当于"30×30 像素以上都算物料"，几乎等于没有面积过滤——这是误识别最多的来源之一。

每块物料的 `solidity / mass_ratio / contour_circularity / hole_ratio /
equivalent_diameter` 都会打进工具 JSON，实拍后按读数收紧即可。

## 7. 颜色标定（可选，但想更准就该做）

判色用的是"色块内芯均值"到各色号原型的距离。原型默认取 `hsv_ranges` 的中心，
所以**不标定也能跑**；但真实物料的色相/饱和度往往偏离区间中心（尤其浅蓝和黑），
采样一次能明显提升判色准确度。

在实时工具窗口里：

1. 鼠标移到目标物料上（不动鼠标则取当前最大的一块）；
2. 按 `1`~`6` 把它记成该色号的原型，终端回一行 `PROTOTYPE_LOCKED`；
3. 六个色号都做完，按 `w` 写回 `config/jetson.json`（先备份，回 `PROTOTYPES_SAVED`）。

写入的就是 `colors.<id>.prototype_hsv: [H, S, V]`，可手改或删掉退回区间中心。

两点要记住：

- 原型是在**归一化之后**的画面上采的，所以换灯、换场地基本不用重标（这正是归一化的价值）；
  只有同一批物料本身有色差时才需要重标。
- 原型只影响"判成哪个色号"，**不影响掩码**。若标定值与 `hsv_ranges` 差太远，物料像素可能
  根本不进掩码，此时要同时放宽该色号的区间（掩码负责圈出物料，原型负责判色）。

平面标定（`config/calibration.json` 的像素→毫米单应）是另一回事：它只决定输出单位是 `PX`
还是 `MM`，不影响颜色判准。单应矩阵与相机位姿、平面高度一一对应，转盘面/粗加工区/暂存区
是不同高度的平面，一个矩阵换不了场景，相机高度一变就要重标。

## 8. 想改视场（画面大小）

**视野由“镜头焦距 + 相机到工作面的距离”决定，与分辨率无关。** 固定高度后只有这几条路：

| 目标 | 手段 | 代价 |
|---|---|---|
| 上下看得更多（不改硬件） | 切采集档位 `wide_4_3`，见 8.1 | 需重画 ROI，清晰度略降 |
| 左右也看得更多 | 换短焦 M12 镜头，或把相机挪远/挪低 | 畸变增大、物料像素数下降 |
| 只把画面放大 | `zoom_absolute`（1.0×~2.0×），见 8.2 | 只会更窄，且控件不稳定 |

切换档位：

```bash
python3 tools/test_turntable_color_live.py --task-code 156+123+516+231 \
  --batch 1 --target 1 --capture-profile wide_4_3
# 或改 config/jetson.json -> camera.capture_profile: "default" | "wide_4_3"
```

### 8.1 采集档位（推荐做法）

这颗相机是 **5 MP / 4:3 传感器（2592×1944）**，而 1280×720 是 **16:9 上下裁切**。
配置里已经备好两档：

| 档位 | 分辨率 | 帧率 | 视场 | 清晰度 |
|---|---|---|---|---|
| `default` | 1280×720 | 60 | 水平 1.00× / 垂直 1.00× | Laplacian 4.6（裁切，最锐） |
| `wide_4_3` | 1280×960 | 50 | 水平 **1.00×** / 垂直 **1.33×** | 3.3（传感器 1/2 读出） |

**实测依据**（静止场景、zoom=0、1:1 全分辨率相关）：

| 假设 | 相关系数 | 平均绝对差 |
|---|---|---|
| 720p = 960 的正中 720 行（裁切） | **0.957** | 4.62 |
| 720p = 960 整幅压扁成 16:9 | 0.434 | 19.08 |

→ 720p 是上下裁切，所以 `wide_4_3` 真的多看 33%，水平视场与像素密度都不变
（同一物料在两个档位下的像素宽度完全一样）。更高分辨率档
（1600×1200 / 2048×1536 / 2592×1944）视场一样、只会更软更费算力，不建议用。

切档的四个注意点：

1. `fps` 会跟随档位自动解析（`wide_4_3` 最高 50），不需要手改；
2. `scenes.*` 的 ROI 全是绝对像素，**必须用 `tools/pick_roi.py` 重画**；
3. 圆环数字模板吃清晰度，切档后重采 `tools/capture_ring_digit_templates.py`；
4. 平面标定按分辨率算，已有标定后切档会打印 `CALIBRATION_SIZE_MISMATCH` 提醒；
   工具的基准点已改成“配置尺寸的一半”，不用再手改 `--reference-x/y`。

### 8.2 数字变焦（只能变窄，且不稳定）

`zoom_absolute`（0~60 ≈ 1.0×~2.0×）是中心裁切，**永远不能变宽**；而且这颗相机在流还没建立时
写这个控件会返回 `EIO`，所以它被列入 `camera.v4l2_controls_optional`：写失败只告警、不阻断启动，
并且在相机出流后会**自动重试一次**（正常启动流程里它其实能写成功）。要临时试：

```bash
CAM="$(python3 -c 'import json;print(json.load(open("config/jetson.json"))["camera"]["device"])')"
v4l2-ctl -d "$CAM" --set-ctrl=zoom_absolute=30     # 用完记得改回 0
```

另外注意：`competition_locked` 档带 `_replace_base: true`，**顶层 `camera.v4l2_controls` 会被整块丢弃**，
只应用该档位里的键——改相机参数要改档位里那一份。

## 9. 什么时候才需要上模型

出现下面任一情况再考虑，且建议只把模型用在"检测/分割"，颜色仍走本链路：

- 决赛物料变成组合体、任意姿态、强遮挡，形状/轮廓约束失效；
- 需要区分颜色接近但材质不同的同类物料；
- 现场背景出现大量与物料同色的干扰物。

即使那时，输入也应该先做白场归一化，否则模型同样会被光照域偏移打崩。
